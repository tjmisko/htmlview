# Performance

What htmlview costs in memory and time, how that compares with opening the
same page in a browser, and what has and has not helped. All figures are from
one machine and are meant as orders of magnitude, not guarantees.

## Summary

- **The engine is the cost, not the page.** The first window costs about
  110 MiB of private memory: WebKit's web content, UI and network processes.
  A further window sharing that engine costs about 10 MiB, which is roughly
  what the page itself takes.
- **Windows share one engine.** The first `htmlview` becomes a host; later
  invocations hand it their target and exit. Three windows now cost about
  129 MiB private instead of about 340 MiB.
- **Against a browser,** htmlview loads about as fast as cold Chrome and
  about 0.65 s faster than cold Firefox, at a third to a fifth of the memory.
  A browser that is already running opens a window just as fast and adds
  almost no memory.
- **About 110 MiB is the floor for one WebKit window.** Renderer, compositing
  and WebKit feature settings changed nothing measurable. Going lower means
  leaving WebKit.

## Test setup

- Apple Silicon laptop, Asahi Linux (Fedora, aarch64), Hyprland on Wayland,
  15 GB RAM.
- GTK 4.22.5, WebKitGTK 2.54.0, Python 3.
- Page: a 32 KB self-contained HTML document generated by
  [limpid](https://github.com/tjmisko/limpid), with a small probe script
  appended.

### How load time was measured

The probe script waits for the window's `load` event, tries a `fetch()` and an
ES-module `import()` of sibling files, and writes a unique token plus the
results into `document.title`. A harness starts the viewer and polls
`hyprctl clients` every 10 ms until a window with that title appears. Load
time is therefore launch until a visible window shows the fully loaded page,
measured the same way for every viewer.

### How memory was measured

PSS (proportional set size) from `/proc/<pid>/smaps_rollup`, summed over the
viewer's whole process tree, read 2–3 s after load.

PSS splits each shared page among the processes mapping it. WebKit's library
is large and file-backed, so total PSS depends on what else is running: one
htmlview window measured 148 MiB while another WebKit process was open and
246 MiB with none. Anonymous PSS (`Pss_Anon`, labeled "private" below) does
not depend on that, so it is the better figure for what a window really
costs. The browser comparison reports total PSS only.

## htmlview against browsers

Five cold starts each, after one priming run. The browsers ran from fresh,
throwaway profiles with first-run prompts disabled, which is a best case: a
real profile with extensions and session restore starts slower. The htmlview
build predates engine sharing and JIT removal.

| Viewer | Median load | Min–max | PSS | `fetch` / `import` from `file://` |
|---|---|---|---|---|
| htmlview | 0.38 s | 0.38–0.40 s | 148 MiB* | work |
| Chrome, cold | 0.42 s | 0.41–0.43 s | 435 MiB | blocked |
| Chromium, cold | 0.55 s | 0.54–0.56 s | 456 MiB | blocked |
| Firefox, cold | 1.04 s | 1.01–1.09 s | 792 MiB | blocked |
| Firefox, already running | 0.34 s | 0.30–0.35 s | +6 MiB | blocked |

\* Measured while another WebKit process was running, so shared library pages
were split. On its own, a window of that build is about 246 MiB PSS and
114 MiB private.

All three browsers refuse `fetch()` and module imports from `file://` pages.
That is why htmlview exists; self-contained pages such as limpid's don't
depend on it.

## What htmlview does now

**Shared engine.** The first `htmlview` listens on an abstract Unix socket.
Later invocations check the target, send it to the host before loading GTK,
and exit. The host opens a window whose WebView is related to an existing
one, so it joins the same web and network processes. Measured with the
shipped code, JIT off:

| Windows open | Total PSS | Private | Time to open |
|---|---|---|---|
| 1 | 239 MiB | 109 MiB | 0.38 s |
| 2 | 249 MiB | 119 MiB | 0.12 s |
| 3 | 259 MiB | 129 MiB | 0.15 s |

Before sharing, each window was a full copy: about 114 MiB private apiece.

Costs:

- One page crashing the web process takes down every window sharing it.
- Page console output goes to the host process's stderr, not the caller's.
- Windows forced to `--dark` or `--light` get a host of their own, because
  the color scheme is process-wide.

`--separate` (implied by reading from stdin) keeps a fully independent
process.

**No JIT.** JavaScriptCore runs interpreted by default. This saves about
10 MiB, and generated documents don't need JIT speed. `HTMLVIEW_JIT=1` turns
it back on.

## Going lower

About 110 MiB private is the floor for one WebKit window: a sandboxed web
content process with a JavaScript engine, a separate network process even for
local files, and GTK. None of the settings above moved it. A smaller footprint
needs a different renderer: a lightweight HTML engine, a terminal Markdown
pager, or a native viewer. That is outside htmlview's scope as a WebKit
viewer.
